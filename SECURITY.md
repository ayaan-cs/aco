# Security

## Threat model

`aco` executes Python it did not write: rule rewrites of your file and, with `--proposer ollama`, code generated by a language model. It also runs your project's local modules and any third-party packages you list. Treat every candidate as untrusted. The question is what a hostile candidate can reach.

## What contains a candidate

The **sandbox runner** is the boundary. The AST policy in `src/policy.rs` is a pre-filter. It rejects obvious escape routes (`exec`, `eval`, `open`, `getattr`, dunder attributes, imports of `os`, `subprocess`, `socket`, `ctypes` and others, and `sys` beyond a small read-mostly subset) in the script and every local module, so they never cost a sandbox run, but Python has many other paths to the same capabilities. Do not rely on it. Installed third-party packages are not checked at all: numpy and most real packages use `os`, `ctypes` and compiled code, so the sandbox is what contains them.

**Docker** (`src/runner/docker.rs`) runs each candidate in a fresh `python:3.12-slim` container pinned by digest, with:

- `--network none`, so there are no interfaces except loopback
- `--read-only` root, a size-limited tmpfs `/tmp`, and only the harness, the candidate and a copy of the project's local import closure bind-mounted read-only
- `--cap-drop ALL`, `--security-opt no-new-privileges`, and `--user 65534:65534` (nobody)
- `--pids-limit`, `--memory` with equal `--memory-swap`, `--cpus`, and `nofile` and `cpu` ulimits
- no host environment variables (the sandbox sets only `PYTHONHASHSEED` and single-thread BLAS/OpenMP settings), and a wall-clock timeout that runs `docker kill`

Docker is the portable boundary and the one to use on macOS.

**unshare** (`src/runner/unshare.rs`) is the Linux fallback:

- new user, mount, PID and network namespaces (the network namespace has only a downed loopback)
- a private tmpfs root that holds a read-only bind of `/usr`, the harness and candidate read-only at `/work`, the project snapshot read-only at `/proj`, installed packages read-only at `/deps`, a tmpfs `/tmp`, `/dev/null` and a fresh `/proc`. `pivot_root` and a lazy unmount detach the host root, so host files outside `/usr` are not reachable
- `setpriv --no-new-privs` with empty inheritable, ambient and bounding capability sets before the candidate starts
- `env -i`, so only `PATH` and a temporary `HOME` remain
- `prlimit` limits for CPU seconds, address space, file size, process count and open files, plus a wall-clock timeout that kills the process group. `--kill-child` makes the namespace's init die with `unshare`, which takes every process in the PID namespace with it

**Project files** are copied into a fresh temporary directory (only files in the import closure; never `.git`, virtualenvs or caches; at most 1,000 files and 20 MB; paths with characters that could confuse a mount option are refused) and mounted read-only, so a candidate cannot change your source tree. The copy is deleted after the run.

**Package installs** are the one step with network access. They run before any candidate, outside the sandbox, as `pip install --only-binary=:all: --isolated --no-input` into a cache directory (unshare) or a `docker build` from the pinned base (Docker). Wheels only means no package build scripts (`setup.py`) run on your machine; requirements with URLs, paths or pip options are refused. Installing a wheel does not execute it, but the package's code then runs inside the sandbox on every candidate, under the same limits and with no network. The host `python3` is otherwise used only to check that a file parses (for a clearer error) and to run pip.

If unprivileged user namespaces are unavailable, the runner refuses to run (fails closed) and names `kernel.unprivileged_userns_clone` and `kernel.apparmor_restrict_unprivileged_userns`. It never changes those settings and never falls back to running without isolation.

## Residual risk

- **Kernel bugs.** Both sandboxes share the host kernel. A kernel exploit can escape either one. Unprivileged user namespaces in particular expose more kernel surface than Docker's default seccomp profile, and the unshare runner adds no seccomp filter.
- **`/usr` is readable** inside the unshare sandbox, so a candidate can see which software is installed.
- **Resource use.** Limits bound one candidate, but `--jobs` candidates run at once and the timed work still uses real CPU.
- **Oracle, not proof.** A rewrite that prints the same output can still behave differently on other inputs. A confirmed winner that includes a model rewrite is flagged for review.
- **Packages you list are trusted to install.** A malicious wheel on PyPI cannot run code at install time, but it does run inside the sandbox, and the package cache is shared between runs (`~/.cache/aco`, or the `aco-deps:*` images).
- **Not a service.** `aco` is a single-user developer tool. Do not expose it as a multi-tenant service, and do not run it on Python files from the internet.

## Reporting

Please report vulnerabilities privately through GitHub's "Report a vulnerability" on https://github.com/ayaan-cs/aco rather than in a public issue.
