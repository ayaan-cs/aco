# Security

## Threat model

`aco` executes Python it did not write: rule rewrites of your file and, with `--proposer ollama`, code generated by a language model. Treat every candidate as untrusted. The question is what a hostile candidate can reach.

## What contains a candidate

The **sandbox runner** is the boundary. The AST policy in `src/policy.rs` is a pre-filter. It rejects obvious escape routes (`exec`, `eval`, `open`, `getattr`, dunder attributes, imports of `os`, `sys`, `subprocess`, `socket`, `ctypes` and others) so they never cost a sandbox run, but Python has many other paths to the same capabilities. Do not rely on it.

**Docker** (`src/runner/docker.rs`) runs each candidate in a fresh `python:3.12-slim` container pinned by digest, with:

- `--network none`, so there are no interfaces except loopback
- `--read-only` root, a size-limited tmpfs `/tmp`, and only the harness and candidate bind-mounted read-only
- `--cap-drop ALL`, `--security-opt no-new-privileges`, and `--user 65534:65534` (nobody)
- `--pids-limit`, `--memory` with equal `--memory-swap`, `--cpus`, and `nofile` and `cpu` ulimits
- no host environment variables, and a wall-clock timeout that runs `docker kill`

Docker is the portable boundary and the one to use on macOS.

**unshare** (`src/runner/unshare.rs`) is the Linux fallback:

- new user, mount, PID and network namespaces (the network namespace has only a downed loopback)
- a private tmpfs root that holds a read-only bind of `/usr`, the two files read-only at `/work`, a tmpfs `/tmp`, `/dev/null` and a fresh `/proc`. `pivot_root` and a lazy unmount detach the host root, so host files outside `/usr` are not reachable
- `setpriv --no-new-privs` with empty inheritable, ambient and bounding capability sets before the candidate starts
- `env -i`, so only `PATH` and a temporary `HOME` remain
- `prlimit` limits for CPU seconds, address space, file size, process count and open files, plus a wall-clock timeout that kills the process group. `--kill-child` makes the namespace's init die with `unshare`, which takes every process in the PID namespace with it

If unprivileged user namespaces are unavailable, the runner refuses to run (fails closed) and names `kernel.unprivileged_userns_clone` and `kernel.apparmor_restrict_unprivileged_userns`. It never changes those settings and never falls back to running without isolation.

## Residual risk

- **Kernel bugs.** Both sandboxes share the host kernel. A kernel exploit can escape either one. Unprivileged user namespaces in particular expose more kernel surface than Docker's default seccomp profile, and the unshare runner adds no seccomp filter.
- **`/usr` is readable** inside the unshare sandbox, so a candidate can see which software is installed.
- **Resource use.** Limits bound one candidate, but `--jobs` candidates run at once and the timed work still uses real CPU.
- **Oracle, not proof.** A rewrite that prints the same output can still behave differently on other inputs.
- **Not a service.** `aco` is a single-user developer tool. Do not expose it as a multi-tenant service, and do not run it on Python files from the internet.

## Reporting

Please report vulnerabilities privately through GitHub's "Report a vulnerability" on https://github.com/ayaan-cs/aco rather than in a public issue.
